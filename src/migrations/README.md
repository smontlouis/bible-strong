# Application migrations

`appMigrationOrchestrator.ts` is the public seam for mandatory application migrations. Callers inspect one phase and scope, present the returned plan, then invoke `run` or—only after a failure—`abandon`. One `run` executes only the plan returned by `inspect`; callers inspect again after completion to present the next migration in deterministic order.

Migration definitions provide deterministic, serializable plans, idempotent step execution and an explicitly idempotent terminal finalizer. Destructive or resource-specific cleanup is declared in `plan.cleanupSteps` and executed through the finalizer's `runCleanupStep` helper. Each cleanup resource is checkpointed and observed independently; the orchestrator refuses to terminate while a declared cleanup step is incomplete. Cleanup checkpoints are tied to their terminal outcome and restart from the beginning if a failed completion is changed to abandonment. The finalizer itself may be replayed after interruption, so every cleanup operation and any remaining non-resource housekeeping must be idempotent.

A registered definition must remain available at the same ID, version and phase until every execution has reached a terminal outcome. Multiple versions may be registered together—with one shared order per ID and phase—so an interrupted older execution can finish before the newer version is presented. Missing definitions for active persisted executions fail closed; terminal history may outlive its definition.

Local migrations use the device scope and run before normal application access. Account migrations use the authenticated user ID as their scope and run only after authentication. A definition may use the `recheck` completion policy when legacy input can reappear, as with embedded Firestore data from an older device.

Persisted state is schema-versioned and stored by `mmkvMigrationStateStore.ts`. Detection is checkpointed before the transition to awaiting confirmation. An abandonment decision is also checkpointed before cleanup and resumed until it reaches its terminal outcome. Unknown, corrupt or state-machine-inconsistent state fails closed so a destructive migration is never silently skipped or restarted. The store owns a process-wide runner lock shared by adapters using the same MMKV key. Plans and lifecycle events contain technical resource identities only; user Bible text, notes and other user-authored content must never be included.
