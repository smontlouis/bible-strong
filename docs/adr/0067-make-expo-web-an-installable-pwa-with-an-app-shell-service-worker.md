# ADR-0067: Make Expo Web an installable PWA with an app-shell service worker

## Status

Accepted. Extends [ADR-0047](./0047-host-expo-web-on-cloudflare.md). Leaves the Web content
rules of [ADR-0063](./0063-serve-offline-copies-only-to-native-attestations.md) and
[ADR-0065](./0065-protect-resources-without-mandatory-attestation.md) unchanged.

## Context

`web.bible-strong.app` is Expo's single-page export served by Cloudflare Workers Static Assets.
It had no manifest, no service worker and the default Expo HTML template, so it could not be
installed and showed nothing without a network. Every asset was served with
`max-age=0, must-revalidate`, even content-hashed bundles. The web entry bundle was 25.2 MB,
close to Cloudflare's 25 MiB per-file limit.

The Web client is online-only for editorial content: it never installs Offline copies, and
Resource API responses are not meant to be stored for offline reading.

## Decision

Make the Web client an installable PWA whose service worker caches the application shell only.

- **Install metadata.** `apps/expo/public/` holds `index.html` (English `lang`, `viewport-fit=cover`,
  light/dark `theme-color`, standalone metas), `manifest.webmanifest` (`start_url: /home`,
  `display: standalone`, any + maskable icons) and icons generated by `web:icons`. The page keeps
  `theme-color` on the selected app theme at runtime.
- **Headers.** `public/_headers` serves `/_expo/static/*` and `/assets/*` (content-hashed) as
  `immutable`, and revalidates `/sw.js` and the manifest.
- **Service worker.** Serwist, the maintained Workbox fork. `service-worker/sw.ts` is bundled with
  esbuild and receives its precache manifest from `@serwist/build` in `scripts/build-web-sw.mjs`,
  run by `web:export` and `web:build`. The precache holds `index.html`, the manifest, icons, every
  `_expo/static` JS/CSS chunk and the fonts awaited before the first paint, within a 30 MiB budget.
  Navigations are network-first with a 4 s timeout and fall back to the precached shell. Other
  same-origin hashed files are cached on first use. Cross-origin requests (Resource API, Firebase,
  analytics, CDNs) and non-GET requests are never handled.
- **Updates.** A new worker waits. The page checks for updates when it becomes visible and hourly,
  and shows a reload banner; accepting it sends `SKIP_WAITING` and reloads once the new worker
  controls the page. The worker is registered only by production builds; development builds
  unregister any worker left on the same origin.
- **Bundle.** Heavy libraries are imported per module (lucide icons, date-fns functions and
  locales) and the web date picker and assistant are lazy-loaded, which brings the entry to
  18.9 MB. Expo Router async routes and Metro tree shaking were measured and not adopted: the
  first moves shared code into an equally large common chunk, the second is still experimental
  in SDK 56 and needs about 7 GB of memory per export.
- **Computers install, phones get the native apps.** The installable PWA targets computers.
  On phones and tablets, an inline script in `index.html` cancels `beforeinstallprompt`, iOS Safari
  shows Apple's Smart App Banner (`apple-itunes-app`, `app-argument=biblestrong://<route>` so an
  installed app opens the same screen), and other mobile browsers and home-screen web apps show a
  dismissible in-app banner linking to the App Store or Google Play, snoozed for 30 days once
  closed. The manifest and service worker stay on every device: manual installs keep working,
  they are just no longer promoted. `prefer_related_applications` was not used because Chrome
  would then refuse to install the PWA on computers too.
- **Gate.** `scripts/check-pwa.mjs` validates the export (manifest, icons, HTML links, headers,
  same-origin precache within budget) before every production deployment.

## Consequences

The Web client can be installed on computers, starts offline on every device, and shows the
existing offline states instead of failing. Mobile visitors are steered to the native apps, which
remain the full offline experience. Content stays online-only and no API response is cached, so
the protections of ADR-0065 are unaffected.

A service worker can keep users on a stale build. Network-first navigations, a revalidated
`sw.js` and the reload banner limit this. To retire the worker, deploy a `sw.js` that unregisters
itself and clears its caches. Deleting `sw.js` does not work: the SPA fallback answers with HTML,
the browser rejects the update and keeps the old worker.

Google and Apple sign-in still use `signInWithPopup` against the `firebaseapp.com` auth domain.
In an iOS home-screen app the popup may not return the credential. Fixing it requires serving
Firebase's `/__/auth` handler from `web.bible-strong.app`, switching `authDomain`, using the
redirect flow in standalone mode and registering the new redirect URIs with Google and Apple.
